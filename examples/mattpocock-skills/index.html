ask-matt

知道遇到了什么问题，却记不住该用哪个技能。

场景、输入、流程与边界

必要输入：当前处境、已有材料；必要时说明是否在工作目录中。

自带流程：先读相关技能原文，再建议主路线、旁路或独立能力；在阶段边界考虑上下文处理。

预期产物：技能选择建议与路线解释。

最小请求：/ask-matt 我有一份已经讨论清楚的规格，下一步该用哪个入口？

边界：它是用户调用的路由器，只提示下一入口，不替用户调用另一个用户入口。

边界：提示驱动而非确定脚本；已有 CLAUDE.md 时不另外创建 AGENTS.md；不得覆盖用户周边内容。

grilling

一个决策包含多层依赖，容易在前置未定时乱问后续细节。

场景、输入、流程与边界

必要输入：当前决策树、已知事实与用户真实选择。

自带流程：每轮询问前置已定的整组前沿问题，附建议；收到真实回答后重算前沿；环境事实由 Agent 核对。

预期产物：逐轮澄清与已达成共同理解的决策树。

最小请求：/grilling 检查这套方案的决策依赖。

边界：依赖同轮未决问题的后续问题应留到下一轮；不代替用户回答。

domain-modeling

同一个词在讨论里指向不同对象，代码和描述也可能冲突。

场景、输入、流程与边界

必要输入：当前用词、项目术语表、实际代码行为与相关 ADR。

自带流程：挑战歧义，用具体边界场景核对；术语一旦确定就记入 GLOSSARY.md；重大取舍才考虑 ADR。

预期产物：清晰的领域词汇与少量必要的决策记录。

最小请求：/domain-modeling 这里“资料”同时指原文件和索引条目，请帮我区分。

边界：术语表不是规格或实现笔记；ADR 要同时满足难逆转、缺上下文会意外、确有取舍。

to-spec

需求已讨论清楚，希望形成可交给后续实现的规格。

场景、输入、流程与边界

必要输入：当前讨论上下文、仓库理解、已配置的任务追踪方式。

自带流程：核对项目与测试接口位置，确认测试位置，再按模板综合问题、解决方案、故事、实现和测试决定、范围外内容，发布规格。

预期产物：可交付规格，按配置进入任务追踪并标记 ready-for-agent。

最小请求：/to-spec 把已经确认的讨论整理成规格。

边界：原文明确不是新一轮需求访谈；测试接口确认不等于重新 grill 全部需求。通常不写具体文件路径与代码，原型决策片段是例外。

to-tickets

规格较大，需要分成能在独立新会话中完成的任务。

场景、输入、流程与边界

必要输入：规格、计划或可用讨论；有引用时读取全文与评论；任务追踪配置。

自带流程：提出贯穿各层的窄完整切片，声明阻塞关系；用户审核粒度和依赖后，再按追踪方式发布。

预期产物：逐个可验收的任务、验收条件和明确阻塞边。

最小请求：/to-tickets 把这份已确认规格拆成任务。

边界：不是数据库、接口、页面各一张的水平分层；跨全仓机械迁移可用 expand–contract 例外；不关闭或修改父任务。

wayfinder

项目太大、跨多次会话，连决定之间的路线也还看不清。

场景、输入、流程与边界

必要输入：目标目的地、当前前沿和未能精确表达的未定事项。

自带流程：建立索引地图与决定任务，声明依赖，逐次认领、解决和记录；新发现再进入前沿。

预期产物：已解决的决定、链接索引和可交给规格阶段的清晰路线。

最小请求：/wayfinder 我想建设资料检索平台，但尚不清楚数据治理和部署约束。

边界：默认产出决定而非直接完成项目；一般一次会话只解决一个决定任务，研究任务例外；不把所有大型已明确任务都当迷雾。

implement

已有一张明确任务或一份范围清楚的规格。

场景、输入、流程与边界

必要输入：规格或任务；明确引用；已确认的测试接口位置。

自带流程：读取任务并报告题名，在可用接口位置用 tdd 实现；常跑类型和相关测试，结束跑全量，调用 code-review 后提交当前分支。

预期产物：已实现、验证、审查并提交的本段工作。

最小请求：/implement 实现这张已经确认的任务：<任务引用>。

边界：不是替需求澄清；原文要求审查和提交，真实操作仍要满足当前会话授权与仓库要求。

implement-spec

规格已有任务图，想让就绪任务并行推进后集成。

场景、输入、流程与边界

必要输入：规格、关联任务及其阻塞关系、任务追踪配置。

自带流程：建立集成分支，工作树实现者在就绪前沿推进，完成后合并；更新前沿；全部完成后审查集成分支并清理。

预期产物：落在单一集成分支上的整份规格，以及按追踪规则解决的任务。

最小请求：/implement-spec 按这份规格及其任务图实施。

边界：不是把任意任务同时发出去；有阻塞边、有分支同步与合并；草稿 PR 以追踪规则或用户要求为条件。

tdd

接口行为明确，想先用测试固定该行为再实现。

场景、输入、流程与边界

必要输入：公开行为及与用户预先确认的测试接口位置。

自带流程：写独立预期的失败测试，再写最少实现使其通过；一次一个纵向切片，通过公开接口观察行为。

预期产物：与公开行为相符、能在实现重构后继续成立的测试和代码。

最小请求：/tdd 在已确认的检索接口位置，先实现一个“能按标题找到资料”的行为。

边界：当前入口原文把重构放到 review 阶段，不放进红绿实现循环；不能从 README 的一般描述推成循环内强制重构。

prototype

纸面讨论无法判断状态规则或界面形式是否合适。

场景、输入、流程与边界

必要输入：具体设计问题和相关项目上下文。

自带流程：逻辑问题走单文件 HTML；界面问题走多个差异显著的方案；显露状态，简单运行，再把得到的决定与原型证据保存。

预期产物：可运行的试验原型、所回答的问题及判定结果。

最小请求：/prototype 用一个小原型检查筛选条件切换后，选中资料的状态是否合理。

边界：不是生产实现；默认内存状态，不先做完整架构、测试与持久化；throwaway 不表示销毁证据。

wizard

有 Agent 无法代劳的账号或仪表盘操作。

diagnosing-bugs

遇到难复现的错误、偶发故障或性能回退。

场景、输入、流程与边界

必要输入：用户症状、复现条件与可访问环境。

自带流程：建立能对该症状变红的紧反馈命令，复现并最小化，列可证伪假设，逐变量取证，修复并做回归与清理。

边界：反馈环没有建立前不跳到猜原因；敏感输出先脱敏；无有效测试接口位置应如实报告。

triage

有外部错误报告或功能请求，需要判断如何处理。

code-review

要判断分支或 PR 自某个固定基点以来的改动。

场景、输入、流程与边界

必要输入：可解析且非空的固定点差异、规格来源、仓库编码标准。

自带流程：固定基点，找需求与标准，两个独立审查分别检查 Standards 和 Spec，再并列报告。

预期产物：分开的规范与需求发现、各轴严重问题。

最小请求：/code-review 审查这条分支自 <固定基点> 以来的改动，规格在 <规格引用>。

边界：规范通过不代表需求通过；不能用相互抵消的综合评分掩盖一轴失败；当前来源缺规格时明确说明该轴跳过。

codebase-design

接口太复杂，理解一个行为要跳很多文件，或测试越过接口。

场景、输入、流程与边界

必要输入：模块的调用方、接口知识负担、行为与实际变化点。

自带流程：用 module、interface、depth、seam、adapter 等共享词汇设计形状；按删除测试、接口即测试面等原则核对。

预期产物：更清晰的模块接口、位置与可测性判断。

最小请求：/codebase-design 检查资料检索模块的接口是否把太多内部细节交给调用者。

边界：深度不是代码行数比；一个适配器不自动构成真实变化位置；接口包含调用者必须知道的约束与错误模式。

pr

要写一份让审阅者快速理解的 PR 描述。

场景、输入、流程与边界
